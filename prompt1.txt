# Culturio — Coding Agent Prompt 1
## Monorepo Foundation, Data Ingestion & Media Processing

### 1. Project overview

You are implementing the foundational infrastructure for **Culturio**, an open-source digital archive of historical African artifacts.

Culturio has two planned experiences:

1. **Digital Gallery:** A Pinterest-inspired, image-heavy gallery for discovering physical African historical artifacts.
2. **Virtual Museum:** An immersive 3D museum built with Three.js and Threlte.

This task covers **only the monorepo foundation, database, ingestion pipeline, image processing, storage integration, and automation**.

Do not implement the digital gallery, 3D museum, or their interfaces yet. These will be implemented in separate phases.

The project is also an engineering learning exercise focused on performant image delivery, browser rendering, and Three.js.

Prioritize maintainability, correctness, measurable performance, and production-oriented engineering practices without introducing unnecessary infrastructure.

Do not introduce a separate backend service, message broker, Redis, or external job-processing platform.

The ingestion pipeline must run independently of the SvelteKit application.

### Cloudflare integration

Use the current supported Cloudflare Workers and D1 tooling.

For ingestion running outside Cloudflare Workers:

- Use Cloudflare's authenticated D1 HTTP API for remote database operations.
- Use R2's S3-compatible API for object uploads.
- Keep all credentials server-side.
- Implement bounded batch operations.
- Respect API request limits and handle rate limiting.
- Avoid using Wrangler CLI subprocesses for individual database writes.

The ingestion system must not depend on the web application being deployed.

## 4. Data sources

Implement an extensible adapter system.

### Initial sources

**Metropolitan Museum of Art**

API documentation:
https://metmuseum.github.io/

Use its public collection API.

**Smithsonian Open Access**

https://www.si.edu/openaccess

Use the supported public API and authentication mechanism.

### Adapter interface

Each source adapter must support:

- Discovering candidate African artifacts.
- Fetching complete records.
- Normalizing source-specific identifiers.
- Extracting artifact metadata.
- Extracting image metadata and licensing information.
- Tracking pagination or progress.
- Handling rate limits.
- Reporting source errors.

Do not assume that all museums provide equivalent metadata.

Use source-specific normalization rules.

### Geographic scope

Cover all African regions, including:

- North Africa
- West Africa
- Central Africa
- East Africa
- Southern Africa

Do not rely exclusively on modern country names.

Historical civilizations, cultures, and geographical regions may cross modern national boundaries.

Do not classify an artifact as African solely because its description contains the word "Africa".

Use reliable source metadata and explicit mapping rules.

Ambiguous records should be marked for review.

### Initial ingestion target

Target 500–1,000 unique, valid artifacts.

Support configurable limits:

```bash
pnpm ingest --source met --limit 100
pnpm ingest --source smithsonian --limit 100
pnpm ingest --source all --limit 1000
```

The limit must apply to successfully processed records, not merely fetched API responses.

Do not invent records to meet the target.

## 5. Database architecture

Design a normalized relational schema using Drizzle ORM for Cloudflare D1.

### Required entities

**Artifacts**

Canonical Culturio artifact records.

Fields should include:

- ID
- Slug
- Primary title
- Alternative names
- Description
- Artifact type
- Culture
- Civilization
- Country or geographical origin
- Historical period
- Earliest and latest estimated creation dates
- Date display text
- Materials
- Dimensions
- Publication status
- Quality score
- Created timestamp
- Updated timestamp

Historical dates must support uncertainty and BCE dates. Do not invent precise dates from approximate descriptions.

**Artifact Sources**

Store each museum's record independently from the canonical artifact.

Include:

- Source institution
- External identifier
- Source URL
- Accession number
- Raw metadata reference or payload
- Last fetched timestamp
- Source-specific attribution
- Source record hash

Enforce uniqueness on the combination of source and external identifier.

**Artifact Images**

Support multiple images per artifact.

Include:

- Image ID
- Artifact ID
- Source record ID
- Original source URL
- Original width and height
- MIME type
- Dominant color
- Content hash
- R2 object keys
- Variant dimensions
- License
- Attribution
- Publication status
- Processing timestamp

Store image variants in a related table or another appropriately normalized structure if necessary.

**Cultures and Civilizations**

Represent these as separate entities where useful.

Avoid forcing every artifact into exactly one civilization.

**Ingestion Runs**

Track:

- Run ID
- Source
- Start/end timestamps
- Status
- Records discovered
- Records processed
- Records inserted
- Records updated
- Records skipped
- Records rejected
- Images processed
- Errors encountered

**Ingestion Checkpoints**

Store enough progress information to resume interrupted operations safely.

**Review Records**

Store records requiring manual inspection, including the reason for rejection or review.

### Database constraints

Implement:

- Foreign keys.
- Unique constraints.
- Appropriate indexes.
- Transactional operations where supported.
- Deterministic upserts.
- Referential integrity.

Do not create duplicate artifacts when ingestion is repeated.

Deduplication must distinguish between exact source-record identity and uncertain cross-institution artifact matches.

Never merge two records solely because their titles match.

When identity cannot be established confidently, preserve separate records.

Prepare the database for this now.

Create an FTS5 virtual table indexing:

- Artifact title
- Alternative names
- Description
- Culture
- Civilization
- Country
- Historical period

Use an external-content FTS5 table where appropriate.

Implement synchronization triggers for insert, update, and delete operations, along with an initial index rebuild.

Ensure that D1 supports the chosen FTS5 schema and migration operations.

Provide a reusable search query function that supports:

- Relevance ranking using BM25.
- Pagination.
- Safe user-query handling.
- Published-record filtering.

Use parameterized queries and correctly handle FTS5 query syntax.

The gallery search UI is out of scope.

## 7. Image ingestion and optimization

This is a critical part of the project.

Images must be downloaded, inspected, processed, and uploaded to Cloudflare R2.

### Processing workflow

```text
Source Image URL
        |
        v
Download & Validate
        |
        v
Inspect Image Metadata
        |
        v
Calculate Content Hash
        |
        v
Check Existing Assets
        |
        v
Sharp Processing
        |
        +-- Original
        +-- 320px WebP
        +-- 640px WebP
        +-- 1280px WebP
        |
        v
Upload to R2
        |
        v
Persist Asset Metadata
```

### Sharp requirements

Generate the following variants:

| Variant | Width | Format |
|---|---|---|
| Thumbnail | 320px | WebP |
| Medium | 640px | WebP |
| Large | 1280px | WebP |

Requirements:

- Preserve aspect ratios.
- Do not enlarge low-resolution images.
- Preserve the original image when permitted.
- Apply EXIF orientation correctly.
- Strip unnecessary metadata from public variants.
- Use configurable compression quality.
- Calculate dominant color.
- Record dimensions and output file sizes.
- Avoid unnecessary sharpening.
- Do not apply AI upscaling.
- Do not alter the historical appearance of artifacts.

Use Sharp's streaming or bounded-buffer processing where appropriate.

Do not load hundreds of full-resolution images into memory simultaneously.

### Media safety

Implement:

- Download timeouts.
- Maximum file size limits.
- MIME and decoded-format validation.
- Redirect limits.
- Protection against untrusted download destinations.
- Bounded concurrency.
- Retry policies for transient failures.
- Permanent failure handling for unsupported media.

Treat external API data and media URLs as untrusted input.

## 8. R2 object organization

Use deterministic, content-addressed object keys.

Example:

```text
artifacts/
  {artifact-id}/
    {image-hash}/
      original.jpg
      320.webp
      640.webp
      1280.webp
```

Do not assume every original image is JPEG.

Preserve the correct extension and MIME type.

### CDN delivery

Design the storage integration so public images can be served from a dedicated asset domain, for example:

`assets.culturio.africa`

The actual domain configuration will be performed separately.

Requirements:

- Correct `Content-Type`.
- Appropriate `Cache-Control`.
- Immutable caching for content-addressed assets.
- Public read access only for approved media.
- Private storage access for ingestion.
- No public exposure of R2 credentials.

Do not assume that an R2 bucket automatically provides CDN caching.

Document the Cloudflare custom-domain and cache configuration.

### Image metadata

Persist enough metadata for the gallery to generate responsive `<picture>` or `<img>` elements with:

- `srcset`
- `sizes`
- Width
- Height
- Aspect ratio
- Dominant-color placeholders

The gallery should not need to inspect image files at runtime.

## 9. Licensing and historical integrity

Culturio is open source, but museum images and metadata may have different licenses.

Implement licensing as a first-class part of the ingestion pipeline.

### Requirements

- Preserve original source URLs.
- Preserve institutional attribution.
- Record license identifiers and URLs.
- Distinguish metadata rights from image rights.
- Only upload images to R2 when redistribution is permitted.
- Mark ambiguous licensing for review.
- Preserve provenance information.
- Avoid rewriting historical claims as verified facts.

Do not treat missing licensing information as permission to redistribute.

Where an image cannot legally be hosted, preserve its source reference without copying it.

### Open-source licensing

Use an appropriate software license for the repository.

Document that the software license does not automatically apply to imported cultural heritage content.

Provide an export mechanism for redistributable artifact metadata.

Exclude restricted media and credentials from public exports.

## 10. Ingestion orchestration

The pipeline must be resilient and resumable.

### Required properties

**Idempotency**

Running the same ingestion twice should not duplicate records or media.

**Checkpoints**

Interrupted runs should resume without restarting all completed work.

**Retries**

Use exponential backoff with jitter for transient failures.

Respect `Retry-After` when provided.

**Concurrency**

Configure separate concurrency limits for:

- Museum API requests.
- Image downloads.
- Sharp processing.
- R2 uploads.
- D1 writes.

**Observability**

Use Pino structured logging.

Include:

- Run ID
- Source
- Artifact ID
- Processing stage
- Duration
- Error category

Do not log credentials or sensitive configuration.

**Failure isolation**

A single corrupt image or invalid artifact must not terminate the entire ingestion run.

**Recovery**

Handle partial failures, such as an image successfully uploaded to R2 but its database metadata failing to persist.

Use deterministic keys, retryable operations, and reconciliation to avoid orphaned assets.

## 11. CLI interface

Implement a usable CLI.

Example commands:

```bash
# Ingest records
pnpm ingest --source met --limit 500

# Run all adapters
pnpm ingest --source all --limit 1000

# Validate without publishing
pnpm ingest --source met --dry-run

# Resume an interrupted run
pnpm ingest --resume <run-id>

# Reprocess failed records
pnpm ingest --retry-failed <run-id>

# Rebuild search index
pnpm db:rebuild-search

# Generate ingestion report
pnpm ingest:report
```

Provide clear help output and argument validation.

A dry run must not write to D1 or R2.

## 14. Performance and resource management

The ingestion pipeline should be efficient enough to run on a GitHub-hosted Actions runner.

Avoid:

- Unbounded `Promise.all()` operations.
- Loading all images into memory.
- Reprocessing unchanged images.
- Re-downloading unchanged source records unnecessarily.
- Excessive database round trips.
- Writing every database record individually when batching is appropriate.

Implement configurable resource limits.

Record useful measurements:

- Artifacts processed per minute.
- Average source request latency.
- Image processing duration.
- Original versus optimized image sizes.
- Compression savings.
- R2 upload duration.
- Database write duration.
- Peak process memory where measurable.

Produce a final report containing these measurements.

## 17. Agent operating instructions

Follow these rules throughout implementation:

1. Inspect the existing repository before modifying files. Preserve working code and conventions.
2. Use current stable library versions and verify compatibility, especially SvelteKit, Cloudflare Workers, D1, Drizzle, and Sharp.
3. Do not invent unsupported museum API fields or endpoints. Consult official API documentation.
4. Keep the ingestion pipeline independent of the SvelteKit runtime.
5. Do not introduce unnecessary abstractions or infrastructure.
6. Use typed interfaces and Zod validation at external data boundaries.
7. Keep modules cohesive and testable.
8. Do not hardcode credentials, database identifiers, or deployment-specific values.
9. Do not fabricate successful tests, deployments, or ingestion results.
10. When credentials are unavailable, implement and test against mocks and clearly identify what remains unverified.
11. Do not build the gallery or 3D museum.
12. At the end of each implementation phase, summarize the changes, tests, and outstanding issues.
13. Stop and request clarification when a decision could materially affect licensing, data integrity, or architecture.

### Completion criteria

This phase is complete when:

- The monorepo builds successfully.
- The database schema and migrations work.
- The ingestion CLI operates independently.
- Museum adapters fetch and normalize records.
- Sharp produces optimized images.
- Approved media uploads to R2.
- Artifact metadata persists to D1.
- Duplicate ingestion is handled safely.
- Full-text search infrastructure works.
- GitHub Actions workflows are configured.
- Automated tests pass.
- Documentation explains setup and operation.

**Final deliverable:** A functional, independently executable data ingestion system that supplies normalized artifact records and optimized media for the future Culturio gallery.

Do not begin the gallery or 3D museum implementation until explicitly instructed.
